# 数据清洗规则与运行方式

工程版本 0.2.0；清洗规则版本 1.0.0。
本地程序处理数据，日志、控制台和报告只包含结构、阶段名与聚合稽核，不显示明细示例。

## 输入与输出

输入为项目内 `gacha_db/genshin_gacha.db` 中已导入的 `pulls`，以及必要的维表列。
源库以 `mode=ro` 附加，授权器进一步禁止源表写入和无关列读取。
不重跑导入脚本，不解压原始包，不读取 UID、player_key、源个人路径、原始 JSON 或资源 BLOB。
原导入阶段的拒绝记录只统计数量，不展开或重试。

命令在本项目根目录运行：

```powershell
# 未安装项目时临时使用源码入口；已安装可省略这一行。
$env:PYTHONPATH = 'src;.'
python -m genshin_insight clean
```

默认在本项目 `data/` 生成带时间与随机后缀的新库，及同名 JSON、Markdown 汇总报告。
指定输出时必须使用新的项目内路径：

```powershell
python -m genshin_insight clean --output .\data\cleaned_new.db
```

已有目标库或同名报告会导致运行停止，不覆盖既有产物。源库永不作为写入目标。
处理中使用独占临时库；对账和完整性检查通过才发布为最终文件。
SQLite 排序可使用临时磁盘，运行前应保证充足可用空间。

## 基础校验与标准化

| 项目 | 处理 |
| --- | --- |
| 玩家、数据集、来源、物品、卡池关联 | 必须能关联有效维表；来源所属玩家与数据集必须一致，否则隔离 |
| 来源行号 | 必须为有效整数且不小于 2 |
| 名称 | 仅去首尾空白；空名称、非法物品类型或非法星级的物品不进入维表 |
| 卡池分组 | 使用源卡池维表；必须与原明细声明的分组一致；角色双池共享分组，但保留各自卡池编码 |
| 时间 | 去首尾空白；接受严格秒级无时区时间及 T 分隔，校验真实日历，统一为 `YYYY-MM-DD HH:MM:SS` |
| 时区、日期范围 | 不推断时区，不按未经确认的日期范围删记录；带时区或小数秒格式隔离而不截断 |
| 抽卡 ID | 本地去首尾空白；有值时只接受 ASCII 数字；始终用 TEXT，禁止转换为浮点数 |
| 缺失 ID | 按既有导入代码，数据集 03 必须有 ID，数据集 02 可缺失；不猜测其他数据集规则 |

清洗仅对必要的事实列和维表列操作。数据库中的历史 `summary_*`、`legacy_*`、metadata
及资源载荷不读取、不累计进本次事实或汇总，避免重复计数和历史筛选口径污染。

## 去重与隔离

以下规则在基础校验通过的候选记录中执行，先判定来源行，再判定账号内业务 ID。

1. 相同 `(source_file_id, source_row)` 且玩家、物品、卡池、标准时间和 ID 一致：
   留最小原 `pull_id`，其余记 `duplicate_provenance`。
2. 相同来源行但上述内容冲突：候选记录全部隔离，记 `conflicting_provenance`。
3. 相同 `(player_id, gacha_id)` 且物品、卡池、标准时间一致：
   留最小原 `pull_id`，其余记 `duplicate_gacha_id`。
4. 相同账号和 ID 但内容冲突：候选记录全部隔离，记 `conflicting_gacha_id`，不任选一条。
5. 无 ID 记录不按“时间 + 物品 + 卡池”去重。来源行不同的同秒同物品记录可能属于十连，予以保留。
6. 不读取真实 UID、不按尾号关联、不跨数据集合并账号。

所有被移除或隔离的输入记录均在新库 `dwd_rejected_pull` 登记原 `pull_id` 和固定原因代码；
原始值仍在原始库，可用内部键追溯。一个输入记录只有一个最终去向，稽核逐项对账。

基础隔离代码：`invalid_player_reference`、`invalid_source_reference`、`invalid_source_row`、
`invalid_item_reference`、`invalid_gacha_type`、`pool_group_mismatch`、`invalid_timestamp`、
`invalid_gacha_id`、`missing_gacha_id`。

## 顺序与待复核标记

- 每个 `(player_id, pool_group)` 清洗后从 1 重建连续 `pool_seq`。
- 排序依次使用标准时间、缺失 ID 标记、任意长度数字 ID 的精确数字顺序、来源文件、来源行和原 pull_id。
  缺失 ID 时采用明确的稳定顺序，不把它解释为真实秒内先后。
- 同一秒的分组中，存在缺失 ID 且不止一条记录时，标记 `time_order_ambiguous=1`。
- 导入代码指出部分来源的 `item_type` 可能采用不同编码。
  发现“三星且类型码为 0”的来源时，其全部保留记录标记 `item_type_review=1`。
  记录保留，类型不翻转，多语言名字不自动翻译或合并。
- 类型相关分析须排除待复核来源或显式列为未核实；本次汇总按星级、卡池、日期和物品身份组织。

## 产物表

| 表 | 粒度与用途 |
| --- | --- |
| `dim_dataset`、`dim_player`、`dim_source`、`dim_item`、`dim_gacha_type` | 校验后的维表；不复制个人标识或源个人路径 |
| `dwd_pull` | 一条保留的抽卡记录；含追溯键、连续序号与复核标记；不保留 gacha_id |
| `dwd_rejected_pull` | 一条移除或隔离记录的原 pull_id 与固定原因 |
| `dws_player_pool` | 内部账号 × 合并卡池，统计抽数、星级、时间范围与待复核计数 |
| `dws_pool` | 数据集 × 原卡池，统计抽数、账号数、星级和待复核计数 |
| `dws_daily` | 数据集 × 日期 × 卡池 × 星级 |
| `dws_item` | 数据集 × 卡池 × 原物品身份；多语言物品保持分离 |
| `dq_check_result` | 数量对账、唯一性、序号连续性、外键和完整性检查 |
| `etl_run` | 运行版本、时间与汇总指标，不含明细值 |

这些表属于本地分析层，DWD/DWS 仍可能包含个人粒度，不直接对外发布。
正式出图前需另建 ADS，并依图表制作口径实施小样本及互补抑制。
本次没有进行保底推断、概率估计、首五星/末段截取或真实数据出图。

## 验证

```powershell
python -m pytest
python -m ruff check src test
python -m ruff format --check src test
```

测试使用临时空表及明确合成的虚构记录，不连接真实库。
当前 44 项测试覆盖基础结构、访问边界、日期边界、去重与冲突隔离、十连外观保留、
任意长度数字 ID 排序、原库字节不变、失败不发布、已有产物保护和空输入。

真实运行另检查：输入 = 保留 + 移除/隔离、原因数量一致、去向不重叠、输入完整进入暂存、
池内序号连续、四张 DWS 总数一致、星级数之和一致、外键及 SQLite 完整性。
任何一项失败都不发布清洗库。每次运行的指标与对账结果保存在对应 JSON/Markdown 报告中。
