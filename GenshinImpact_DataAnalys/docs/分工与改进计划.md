## 二、并行与串行关系

**关键路径**：WP1 → WP2 → WP3 → WP5 → WP11

- **可随时并行**：WP7（主题）、WP8（测试）、WP9（文档）、WP10（打包）
- **WP4 与 WP5 在 WP3 完成后可同时开工**，两者只共享"图"和"ADS"，互不写同一文件
- **WP6 可以提前启动**：先用上一版 ADS 调动画与配乐，等 WP2 定稿后再重渲一次

**四个必须串行的耦合点**（分工时最容易踩的坑）：

1. **`ads.py` 一改，全线重跑** —— 图表、报告、答辩、开场片四处消费同一份 ADS。改动必须由一人提交，另外三人拉取后重跑自己那一段。
2. **`defense.py` 与 `speech.py` 必须同一人改** —— 页数和讲稿节数一一对应，改一页不改讲稿就会错位。
3. **`theme/theme.py` 改动同时影响图表和报告插图** —— 换色要两边一起验收。
4. **`pyproject.toml` 是共享文件** —— 各自加依赖前先说一声，避免合并冲突。

在三人方案上再拆：WP5 拆出"讲稿（speech.py）"、WP6 拆出"渲染与配乐（render_opener.cjs / score.py）"，适合分工时间只剩一周、需要并行赶工的情况。

## 四、协作约定（减少返工的六条）

1. **分支**：`master` 保持可交付；功能走 `feat/xxx`、修复走 `fix/xxx`，合并前至少一人看过 diff。
2. **提交粒度**：一次提交只做一件事；消息用 Conventional Commits（`feat:` / `fix:` / `docs:` / `chore:` / `refactor:`）。
3. **点名文件**：提交前 `git status` 逐个确认，不用 `git add .`（仓库里混着几十 MB 视频与产物）。
4. **数据不入库**：清洗库、原始压缩包都在 `.gitignore` 里；交接靠"按文档独立重跑"，所以复现文档是硬前提。
5. **二进制用 LFS**：视频/音频/字体类文件走 LFS 或作为 Releases 附件，不要直接进主干历史。
6. **改动前先看这三份**：`AGENTS.md`（项目边界与授权）、`docs/图表规范.md`（禁止项）、`docs/测试说明.md`（验收方式）。

## 五、可以完善的地方

### P0 · 影响可信度与可复现性（建议先做）

| # | 问题 | 影响 | 做法 | 工作量 |
| --- | --- | --- | --- | --- |
| 1 | **没有 CI** | 测试与规范自检只在本机跑，别人推的东西没人拦 | 加 `.github/workflows/ci.yml`：`pytest` + `ruff check src test` + 一个 `spec_check` 冒烟图 | 2 小时 |
| 2 | **构建清单哈希已过期** | `build_manifest.json` 里 `template_sha256` / `code_sha256` 与现产物对不上，答辩时被问到会露怯 | 重跑一次管道刷新，或在 CI 里加"哈希一致性检查" | 1 小时（重跑另计） |
| 3 | **大二进制直接入库** | 开场片单文件 13 MB，`.git` 已 60 MB 量级；目前没有 LFS、没有 `.gitattributes`，以后每次重渲都会再叠一份历史 | 走 Git LFS，或把成片放 Releases、仓库只留小体积源 | 1–2 小时 |
| 4 | **`.font-cache` 混进仓库** | 两个 10.1 MB 的 TTF 是渲染缓存，白占 20 MB | 删除并写进 `.gitignore` | 半小时 |
| 5 | **渲染依赖没声明** | `playwright` 不在 `pyproject` 里，换机器按文档跑不出开场片 | 补 `dev`/`motion` 依赖 + 渲染说明（含关键帧间隔、白场秒数 `--source-end`） | 1 小时 |

| # | 问题 | 做法 |
| --- | --- | --- |

## 七、如果只挑三件事先做

1. **建 CI**（2 小时）—— 之后所有改动有兜底
2. **清 `.font-cache` + 视频走 LFS**（1.5 小时）—— 仓库立刻瘦 20 MB 以上，后续贡献者克隆不再痛苦
3. **补渲染依赖 + 复现说明**（1 小时）—— 让"换个人也能重渲开场片"成立
