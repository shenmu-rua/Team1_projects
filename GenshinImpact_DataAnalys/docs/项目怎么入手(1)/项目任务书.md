# 数据分析课程项目任务书

组队方式：4 人一组　　提交时间：【由任课老师填写】　　提交方式：【由任课老师填写】　　答辩安排：【由任课老师填写】

## 一、项目目标

以小组为单位，自选一份数据，完成数据接入、清洗、质量评估和业务分析，交付数据质量分析报告和数据分析报告。

这是一份自由度很高的作业。数据、分析问题、技术方案、报告结构和样式都由小组自己决定。除第三部分列出的必做交付物外，硬性要求只有两条：

1. 图表和结论正确，每个数字都能追溯到代码；
2. 数据使用合规，报告和页面不出现个人信息。

项目重点考查三项能力：

1. 把模糊的业务需求改写成能用数据回答的问题；
2. 保证数据和结论可信；
3. 把结论规范、清楚地呈现出来。

## 二、组队与分工

### 2.1 组队

每组 4 人，设组长 1 名，负责进度安排和最终提交。

### 2.2 分工参考

下表仅供参考，小组可以按成员情况调整，也可以轮换。每位组员至少独立负责一部分交付内容。

| 角色 | 主要工作 | 对应交付物 |
| --- | --- | --- |
| 数据 | 找数据、写字段说明、数据接入、质量检查与清洗 | 数据质量分析报告的主体 |
| 分析 | 问题改写、口径定义、子问题分析与出图 | 数据分析报告的正文 |
| 报告 | 报告结构与排版、统一图表样式、全文审校 | 两份报告的成稿；自建报告模板（加分项） |
| 工程 | 代码整理、数据流水线、代码仓库、展示系统 | 分析代码与 README；流水线、展示系统（加分项） |

### 2.3 协作要求

1. **开工先定规范**：约定分析口径、配色、字体和图表样式，写进仓库的说明文件。所有人按同一套规范出图和写作，避免最后拼起来风格和口径不一致。
2. **同一个仓库协作**：全组使用同一个代码仓库，每人用自己的账号提交。提交记录用于核对分工。
3. **数字交叉复核**：每一章的数字，由负责人以外的一名组员对照代码复核一遍。
4. **人人讲得清**：答辩时每位组员都要讲清自己负责的部分，也要能回答关于其他部分的提问。

## 三、交付内容

### 3.1 必做

| 交付物 | 要求 |
| --- | --- |
| 数据质量分析报告 | 说明数据来源与范围；从完整性、规范性、唯一性、一致性、合理性等维度逐项检查，每项给出数字和处理决定；写清清洗规则，清洗前后的行数能对上账；说明样本能代表什么、不能代表什么 |
| 数据分析报告 | 写清业务问题和改写过程；定义分析口径；把问题拆成若干子问题逐一回答，每条结论带数字和口径；最后给出结论、建议和使用边界 |
| 分析代码 | notebook 或 .py 脚本，能从原始数据重新跑出报告中的全部数字和图表 |

两份报告的章节结构和篇幅不做限制，按小组的问题和数据来定。

### 3.2 选做

对外展示系统：把分析结果做成可以打开、可以交互的页面。完成后计入加分。

### 3.3 加分项

| 加分项 | 认定标准 |
| --- | --- |
| 对外展示系统 | 页面能正常运行；每页回答一个问题；页面上的数字与报告一致；只展示汇总结果 |
| 数据流水线 | 清洗、建表、汇总等步骤封装成函数或脚本，一条命令能从原始数据重跑到分析结果；记录每一步的输入、输出行数；阈值、时间窗等业务参数放在配置文件里，不写死在代码中 |
| 自建报告模板 | 自己设计数据质量分析报告或数据分析报告的写作模板，包含章节结构、每节的写作指引、占位内容和格式规范说明；样式按小组自己的配色和图表设计，与课程模板有明显区别；小组的正式报告用这份模板写成 |
| 版本管理 | 有持续的 Git 提交记录，每位组员都有自己的提交；按步骤提交，提交说明写清做了什么；代码托管在 Gitee 或 GitHub |

## 四、选题与保底要求

1. 鼓励各组自选数据。选数据的标准见《项目构建思路》。
2. 也可以使用课堂示范数据（沈阳移动信令）。使用课堂示范数据的小组，按以下规则执行：
   - 在课堂内容之外，至少完成 1-2 项扩展；
   - 只复现课堂内容、没有扩展项的，视为未完成；
   - 总评最高为保底分（【保底分，由任课老师填写】分）。
3. 扩展项可以参考以下方向，也可以自己提：
   - 换一个商圈（太原街或中街）做到访分析，并与西塔对比；
   - 回答一个课堂没讲过的子问题，例如白天活动地分布、不同客群的商圈偏好；
   - 换一种方法完成同一项分析（例如用聚类方法识别停留点），并与课堂方法对比结果差异；
   - 引入外部数据（如地铁站、商场位置）解释分析结论。

## 五、技术要求

### 5.1 分析与可视化（固定）

- 数据处理与绘图使用 pandas + matplotlib，交互图表可以使用 pyecharts 或 plotly（需要有规范）；
- 数据量较大时，允许使用 Polars。

### 5.2 数据存储（不限）

- 数据库不限，可以用 SQLite，鼓励尝试 MySQL、DuckDB 等；
- 数据格式不限，CSV、Excel 等文件都可以。

### 5.3 展示系统（自选）

| 目标 | 推荐技术栈 |
| --- | --- |
| 快速做出原型 | Streamlit、NiceGUI，用 Python 直接写页面 |
| 做得精细 | 前端 Vue 或 React，后端 Django、Flask 或 FastAPI |
| 其他 | 前后端可以自由选择 |

建议先跑通，再逐步优化。

## 六、大模型使用规范

允许使用大模型辅助分析和写作，但必须遵守以下规则：

1. **不发明细数据**：只发字段名、类型、取值范围和汇总结果，不发原始数据文件，不发手机号、身份证号等能识别个人的信息。
2. **数字只来自代码**：报告中的数字只能来自自己运行的代码，不采用大模型给出的数字。
3. **文字逐句核对**：大模型生成或润色的段落，要逐句对照图表和代码结果核对，不一致时以代码结果为准。
4. **判断自己做**：删什么、留什么、口径怎么定、结论怎么下，由小组自己决定，并能讲清理由。
5. **保留记录**：报告附录附上大模型使用记录，写明问了什么、采纳了什么、没采纳什么及原因、怎么验证的。

结论或数字与代码结果不一致的，按内容错误扣分。

## 七、规范要求

### 7.1 图表规范

- 每张图都有编号（如“图 3-1”），标题写结论并带数字，图下写明口径与数据来源；
- 每张图配一段图表解读，写明读图方式、关键发现和对结论的影响，具体要点见两份写作模板；
- 坐标轴、单位、图例完整，图中数字与正文、表格一致；
- 字体、配色、样式结合自己的数据设计，不直接使用软件默认样式；同一类对象在所有图中颜色一致；
- 使用开源字体（如思源黑体、思源宋体），图中中文不能显示为方框。

### 7.2 排版规范

可以参照《数据质量分析报告_写作模板》《数据分析报告_写作模板》排版，也可以自建模板（加分项，见 3.3）。不使用课程模板的，至少做到：

- 有封面、目录和页码；
- 标题分级，并使用 Word 的标题样式，目录能自动生成；
- 正文的字体、字号、行距全文统一；
- 图表按章编号，表题在表格上方，图题在图片下方；
- 报告的配色与图表的配色协调。

模板只规定结构，不规定样式。配色、版式按自己的数据和图表设计，不要与模板或示范报告做成一样。

### 7.3 内容规范

- 每个数字都能找到算出它的代码；
- 每个比例写明分母，每个指标写明口径；
- 写明数据不能回答哪些问题；推断出来的结论注明“推断”；
- 结论不超出样本能代表的范围；
- 遇到反常的数字，先查口径，再下结论；
- 报告和展示页面只出现汇总结果，不出现个人信息；含个人信息的数据和运行结果不提交到代码仓库。

## 八、评分标准（建议）

### 8.1 小组得分

| 项目 | 分值 | 主要看什么 |
| --- | --- | --- |
| 数据质量分析报告 | 30 | 检查维度是否完整；每项检查有数字和处理决定；清洗前后能对上账；样本代表性说清楚 |
| 数据分析报告 | 40 | 问题改写是否合理；口径是否清楚；结论是否正确、带数字、不越界；建议能否对应到结论 |
| 图表规范 | 15 | 按 7.1 逐项检查 |
| 排版规范 | 15 | 按 7.2 逐项检查 |
| **合计** | **100** | |

| 加分项 | 建议加分 |
| --- | --- |
| 对外展示系统 | 最多 +8 |
| 数据流水线 | 最多 +5 |
| 自建报告模板 | 最多 +4 |
| 版本管理 | 最多 +3 |

### 8.2 个人得分

个人总评以小组得分为基础，按以下依据上下浮动（建议不超过 ±10 分）：

- 分工与贡献说明；
- 代码仓库中的个人提交记录；
- 答辩中对本人负责部分的讲解和回答。

在贡献说明和提交记录中都找不到工作内容的组员，由任课老师单独评定。

### 8.3 说明

- 分值为建议值，任课老师可以按班级情况调整；
- 加分后总评不超过 100 分；
- 使用课堂示范数据的小组，总评不超过保底分（见第四部分）。
